# ADR: Job model & lifecycle

Status: Accepted

Date: 2026-04-04

## Context

ADR `0001-v1-scope` established that file operations (copy/move/delete/rename/archive) must be modeled as **cancellable, observable jobs**. ADR `0003-architecture-overview` established UDF-lite per feature and side effects handled outside reducers. ADR `0004-ipc-transport` and the `FileOperations` proto define the streaming contract at the IPC boundary (`JobUpdate` with `oneof` body: progress / log / status).

Before implementing `:core`, we need to decide:

1. **Job identity** — what is a job, what is its stable ID, where does it live.
2. **Job state machine** — valid states and transitions inside the host.
3. **Kotlin representation** — how a running job is represented in `:core` (coroutines, Flow, plain data).
4. **Ownership** — which layer creates, tracks, and destroys jobs.
5. **Persistence** — are jobs persisted across restarts in v1?
6. **Concurrency** — how many jobs can run simultaneously; back-pressure / queue model.

Constraints:
- Kotlin/JVM, Compose Desktop.
- Job progress streams arrive from an **out-of-process plugin** over gRPC (server-streaming).
- The UI consumes job state reactively (Compose `State` / `StateFlow`).
- Multiple jobs may be active concurrently (parallel copy + archive, etc.).
- `:core` must be testable **without** Compose and without a real plugin process.

## Decision

### 1. Job identity

Each job has a **`JobId`**: an opaque string (UUID v4) generated by **the host** at job creation time, before contacting the plugin. The same `JobId` is passed to the plugin in `StartOperationRequest.job_id` and echoed back in every `JobUpdate.job_id`.

Rationale: host-generated IDs allow the host to register the job record and wire UI state before the plugin acknowledges anything.

### 2. Host-side job state machine

The host maintains its own job state, independent of (but driven by) the gRPC stream. Valid states and transitions:

```
PENDING ──► RUNNING ──► COMPLETED
                │──────► FAILED
                │──────► CANCELLING ──► CANCELLED
```

| State | Meaning |
|---|---|
| `PENDING` | Job record created; plugin call not yet initiated or not yet acknowledged |
| `RUNNING` | `StartOperation` stream is open; progress/log updates arriving |
| `CANCELLING` | Host sent `CancelOperation`; waiting for terminal `JobStatusChanged` from plugin |
| `COMPLETED` | Terminal: plugin stream closed with `STATUS_COMPLETED` |
| `FAILED` | Terminal: plugin stream closed with `STATUS_FAILED` or gRPC error |
| `CANCELLED` | Terminal: plugin stream closed with `STATUS_CANCELLED` |

Rules:
- Only the host drives state transitions; UI and plugins observe, not set state.
- A `CANCELLING` job that receives `STATUS_FAILED` (plugin died mid-cancel) transitions to `FAILED`, not `CANCELLED`.
- `PENDING` jobs that never reach the plugin (process launch failed) transition directly to `FAILED`.

### 3. Kotlin representation in `:core`

#### Immutable snapshot — `JobSnapshot`

The UI-facing type is an **immutable data class** consumed via `StateFlow`:

```kotlin
data class JobSnapshot(
    val jobId: JobId,
    val kind: OperationKind,
    val status: JobStatus,           // mirrors state machine above
    val progress: JobProgress?,      // null until first progress update
    val recentLogLines: List<LogLine>, // bounded ring buffer, last N lines
    val errorMessage: String?,       // set on FAILED
    val createdAt: Instant,
    val updatedAt: Instant,
)
```

#### Mutable internal state — `JobHandle`

`:core` owns a mutable `JobHandle` per active job (not exposed outside `:core`):

```kotlin
// Internal to :core
internal class JobHandle(
    val jobId: JobId,
    val scope: CoroutineScope,       // child of plugin-runtime scope
    val updateChannel: Channel<JobUpdate>, // receives updates from gRPC stream
    // ... mutable internal fields
)
```

The `JobHandle` runs a coroutine that consumes the `Channel<JobUpdate>`, mutates internal state, and emits to a `MutableStateFlow<JobSnapshot>`.

#### Public API of `:core` — `JobRegistry`

```kotlin
interface JobRegistry {
    // Returns a snapshot flow for a specific job (or null if unknown).
    fun jobFlow(jobId: JobId): StateFlow<JobSnapshot>?

    // Returns a flow of all currently tracked jobs (active + recent terminal).
    val allJobsFlow: StateFlow<List<JobSnapshot>>

    // Called by :plugin-runtime when a plugin emits a JobUpdate.
    fun onJobUpdate(update: JobUpdate)

    // Called by :plugin-runtime when a plugin stream closes with an error.
    fun onJobStreamError(jobId: JobId, error: Throwable)
}
```

`JobRegistry` is the boundary between `:plugin-runtime` (which drives updates) and `:app-ui` (which observes snapshots). `:core` holds the implementation; `:app-ui` holds a reference via DI.

### 4. Ownership and layer responsibilities

| Layer | Responsibility |
|---|---|
| `:app-ui` | Renders `JobSnapshot` from `StateFlow`; emits user intents (start job, cancel job) |
| `:core` | Creates `JobId`, owns `JobRegistry`, maintains state machine, exposes `StateFlow<JobSnapshot>` |
| `:plugin-runtime` | Calls `StartOperation` on the plugin, forwards `JobUpdate` stream to `JobRegistry`, calls `CancelOperation` on user cancel intent |
| Plugin process | Executes the operation, emits `JobUpdate` over gRPC stream |

The flow for starting a job:

```
UI intent: StartJob(kind, sources, target)
  → :core creates JobId, registers JobHandle in PENDING state
  → :core emits job.created event
  → :plugin-runtime calls plugin.StartOperation(jobId, ...)
  → plugin streams JobUpdate → :plugin-runtime → JobRegistry.onJobUpdate()
  → JobRegistry updates JobHandle → emits new JobSnapshot to StateFlow
  → UI re-renders
```

### 5. Retention of terminal jobs

Terminal jobs (`COMPLETED`, `FAILED`, `CANCELLED`) are **kept in memory** in `JobRegistry` for the session, up to a configurable limit (default: last 50 terminal jobs). This allows the transfers UI to show history without a database.

**No persistence across restarts in v1.** On restart, the job list is empty. Persisting jobs to disk is deferred to a future ADR (requires decisions about storage format and recovery of partial operations).

### 6. Concurrency model

- **No global job queue in v1.** Jobs are started immediately when the user requests them; the plugin decides internally how to handle concurrency (e.g., serialise writes to the same destination).
- Multiple jobs may be `RUNNING` concurrently (one `JobHandle` coroutine each).
- Future ADR may introduce a host-side queue / throttle if user experience requires it.

### 7. Log line buffering

Each `JobHandle` maintains a **bounded ring buffer** of the last `N` log lines (default `N = 200`) in memory. Older lines are dropped. Full log streaming to a file is out of scope for v1.

## Consequences

- `:core` must implement `JobRegistry`, `JobHandle`, `JobSnapshot`, `JobStatus`, and the state machine transitions.
- `:core` depends on Kotlin Coroutines and `kotlinx.coroutines.flow`; no Compose dependency.
- `:plugin-runtime` becomes the producer of `JobUpdate` events; `:core` is the consumer and state owner.
- The `StateFlow<JobSnapshot>` boundary makes `:core` directly consumable from Compose (`collectAsState()`).
- `JobRegistry` interface in `:core` can be faked in unit tests without a real plugin process.
- No job persistence in v1 simplifies `:core` significantly; partial-operation recovery on restart is not handled.
- Bounded log buffer prevents unbounded memory growth for long-running jobs with verbose logging.
